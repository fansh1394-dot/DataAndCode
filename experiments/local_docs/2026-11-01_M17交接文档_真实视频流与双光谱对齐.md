## 4. 任务 A：接入真实视频流（施工步骤）

现有 V4L2 后端已存在（[rk_capture.c](file:///c:/Users/不如喝茶去/Desktop/双光谱毕设/scripts/deploy/rk3588/runtime/rk_capture.c#L150-L242)），但只覆盖了最理想的一档：**单平面 + NV12 + MMAP**。真机摄像头通常不满足这一档，因此按下表逐项补齐，每项都有验收判据。

### A1. 补 fourcc 回退（必做）

现状：`VIDIOC_S_FMT` 强制 `V4L2_PIX_FMT_NV12`，驱动回不到 NV12 直接报错退出。

改动点：`cap_cfg_t` 增 `int fourcc`（或 `char *fourcc_str`），`run_v4l2` 按 `NV12 → YUYV → MJPEG` 顺序试；失败才退出。

- YUYV：`yuyv→NV12` 或直接 `yuyv→BGR`（`pre.c` 里加一个 `yuyv_to_bgr`，YUYV 走 BT.601，系数与 `nv12_to_bgr` 同）。
- MJPEG：走 RK3588 的 `MPP_VIDEO_CodingMJPEG`（`MPP_JPGDEC=y` 已内置），即 `V4L2(MJPEG)→MPP 解 JPEG→NV12`，与现有 MPP 解码后端复用 `pack_nv12` 之后的全部逻辑。

验收：`[CAP:xxx] S_FMT ok <w>x<h> stride=<n> fourcc=<fmt>`，且 `run.log` 帧数与实际出帧一致。

### A2. 补多平面（MPLANE）支持（**CSI/HDMI 的通路前置，必做**）

本轮实测：`rkisp_mainpath`(video22) 与 `stream_hdmirx`(video40) **都是 `V4L2_CAP_VIDEO_CAPTURE_MPLANE`，单平面位为 0**。因此现有单平面实现（`fmt.type = V4L2_BUF_TYPE_VIDEO_CAPTURE`）对这两个节点必然失败。

改动：先 `VIDIOC_QUERYCAP` 读 `capabilities`，按位选 `VIDEO_CAPTURE` 或 `VIDEO_CAPTURE_MPLANE`；后者用 `struct v4l2_buffer` + `struct v4l2_plane planes[2]`，`pack` 时把 `planes[0]`（Y）与 `planes[1]`（UV）分别按 `data_offset`/`bytesused` 拼成打包 NV12。

验收：`VIDIOC_QBUF` 无 `EINVAL`；打包后 Y/UV 首字节采样与 `ffmpeg` 抽帧一致。

### A3. 用驱动时间戳代替 `now_ms()`（**时间同步的前置条件**）

现状：`emit(c, packed, now_ms())` —— 时间戳是「主机发现自己拿到帧的时刻」，含序列化抖动，无法用于双光谱配对。

改动：`VIDIOC_DQBUF` 后判断 `b.flags & V4L2_BUF_FLAG_TIMESTAMP_MONOTONIC`，直接用 `b.timestamp.tv_sec*1000 + tv_usec/1000`；若标志是 `TIMESTAMP_COPY` 则退化为 `now_ms()` 并在日志打一次告警。MPP 侧用 `mpp_frame_get_pts`（单位按 `MPP_TIMESTAMP_SYNC_THRESH` 时基换算），FILE 侧保留 `now_ms()`。

验收：两路 `run.log` 的 ts 差值直方图 p99 ≤ 1 帧间隔；单路连续帧 ts 单调递增、无跳变。

### A4. 补 `VIDIOC_S_PARM` 帧率与缓冲数

现状：请求 4 个 MMAP 缓冲，未设置帧率。

改动：`cap_cfg_t` 增 `nbuf`（默认 4，真机建议 4~6）；`VIDIOC_S_PARM` 设 `timeperframe = 1/fps`（驱动不支持时忽略并告警）。

验收：`fps` 稳定在设定值 ±5%（关闭 `--max-frames` 跑 30 s 统计）。

### A5. 通路切换（命令行不变，只切参数）

```bash
# 单路 USB / HDMI 相机
./rk_stream --model pruned_int8.rknn --rgb-dev /dev/videoX --rgb-size 1920x1080 \
  --ir <同一数据集的 ir.h264> --ir-size 640x512 --fit letterbox --thr 0.25 --fps 30 ...
```

现有逻辑 `cfg.kind = rgb_dev ? CAP_V4L2 : CAP_MPP` 已支持「RGB 真机 + IR 文件」混搭，便于只换一路先验证。

### A6. 验收清单（接入完成的判定）

| # | 判据 | 阈值 |
|---|---|---|
| 1 | 取流不中断 | 连续 30 min，`capture failed` 保持 0 |

### B1. 探针（自包含，零依赖，编译在 `/tmp`）

板上无 `v4l2-ctl`，用下面这段 C 打能力矩阵（`VIDIOC_QUERYCAP` + `VIDIOC_ENUM_FMT` + `VIDIOC_ENUM_FRAMESIZES`）。**只用标准 `<linux/videodev2.h>`，不写任何系统路径。**

```c
// rk_v4l2_probe.c  —— gcc -O2 -Wall -o rk_v4l2_probe rk_v4l2_probe.c
#include <stdio.h>
#include <string.h>
#include <fcntl.h>
#include <unistd.h>
#include <sys/ioctl.h>
#include <linux/videodev2.h>

int main(int argc, char **argv) {
    for (int a = 1; a < argc; a++) {
        int fd = open(argv[a], O_RDWR | O_NONBLOCK);
        if (fd < 0) { printf("%s\tOPEN_FAIL\n", argv[a]); continue; }
        struct v4l2_capability cap;
        memset(&cap, 0, sizeof(cap));
        if (ioctl(fd, VIDIOC_QUERYCAP, &cap) < 0) { printf("%s\tQUERYCAP_FAIL\n", argv[a]); close(fd); continue; }
        const char *kind = (cap.capabilities & V4L2_CAP_VIDEO_CAPTURE_MPLANE) ? "MPLANE"
                         : (cap.capabilities & V4L2_CAP_VIDEO_CAPTURE)        ? "SPLANE" : "OTHER";
        printf("%s\tcard=%s\tdriver=%s\tsingle=%d\tmplane=%d\tstreaming=%d\tkind=%s\n",
               argv[a], (const char *)cap.card, (const char *)cap.driver,
               !!(cap.capabilities & V4L2_CAP_VIDEO_CAPTURE),
               !!(cap.capabilities & V4L2_CAP_VIDEO_CAPTURE_MPLANE),
               !!(cap.capabilities & V4L2_CAP_STREAMING), kind);
        for (int t = 0; t < 2; t++) {
            struct v4l2_fmtdesc f; memset(&f, 0, sizeof(f));
            f.type = t ? V4L2_BUF_TYPE_VIDEO_CAPTURE_MPLANE : V4L2_BUF_TYPE_VIDEO_CAPTURE;
            for (f.index = 0; ioctl(fd, VIDIOC_ENUM_FMT, &f) == 0; f.index++) {
                printf("  [%s] fourcc=%c%c%c%c  %s  compressed=%d\n", t ? "MP" : "SP",
                       f.pixelformat & 0xff, (f.pixelformat >> 8) & 0xff,
                       (f.pixelformat >> 16) & 0xff, (f.pixelformat >> 24) & 0xff,
                       (const char *)f.description,
                       !!(f.flags & V4L2_FMT_FLAG_COMPRESSED));
                struct v4l2_frmsizeenum s; memset(&s, 0, sizeof(s));
                s.pixel_format = f.pixelformat;
                for (s.index = 0; ioctl(fd, VIDIOC_ENUM_FRAMESIZES, &s) == 0; s.index++) {
                    if (s.type == V4L2_FRMSIZE_TYPE_DISCRETE)
                        printf("      %ux%u\n", s.discrete.width, s.discrete.height);
                    else { printf("      step %ux%u ~ %ux%u\n", s.stepwise.min_width,
                                  s.stepwise.min_height, s.stepwise.max_width,
                                  s.stepwise.max_height); break; }
                }
            }
        }
        close(fd);
    }
    return 0;
}
```

### B2. 实测能力矩阵（本轮已用上述探针在板上跑过）

| 节点 | card / driver | 单平面 | 多平面 | STREAMING | 枚举格式 | 尺寸 |
|---|---|---|---|---|---|---|
| `/dev/video22` | `rkisp_mainpath` / `rkisp_v6` | **0** | **1** | 1 | UYVY · NV16 · NV61 · NV21 · **NV12** · NM21 · NM12 | stepwise 32×32 ~ 800×600 |
| `/dev/video40` | `rk_hdmirx` / `rk_hdmirx` | **0** | **1** | 1 | BGR3 · NV24 · NV16 · **NV12** | 不枚举（跟随 HDMI 源） |
| `/dev/video0` `video4` `video11` `video15` | rkcif 系列 | — | — | — | — | **`open` 返回 ENODEV（无 sensor 绑定）** |
| USB UVC `/dev/videoN` | 待插入 | 通常 1 | 0 | 待测 | YUYV / MJPEG | 待测 |

**三条硬结论**：
1. `rkisp_mainpath` 与 `stream_hdmirx` **都只支持 MPLANE**，现有单平面 V4L2 后端**完全驱动不了**这两个节点 → §4 A2 不是「按节点而定」，而是 **接入 CSI/HDMI 的必做前置**。
2. `rkisp_mainpath` 的空口上报 800×600 上限是「无 sensor 时的占位值」，接上 sensor 后必须**复测**，不能沿用。
3. `rk_hdmirx` 不支持尺寸枚举，需先接 HDMI 源、`status=connected` 后再 `S_FMT` 试。

> 判据：**「本机支持 NV12（或已实现回退）」+「STREAMING=1」+「尺寸可配」** 三条同时满足，才允许写进启动参数。

### B3. 三条验证通路（按可行性排序）

**通路 1：USB UVC 相机（最省事，推荐首选）**
1. 插入相机 → `ls /sys/class/video4linux/` 出现新节点（记下编号）。
2. `./rk_v4l2_probe /dev/video<新>` 确认 fourcc/尺寸。
3. 若为 YUYV/MJPEG，先完成 §4 A1 回退；若为 NV12 可直接跑。
4. `./rk_stream ... --rgb-dev /dev/video<新> --rgb-size <尺寸>`，IR 用数据集 `mv_ir.h264`。
5. 判据：出框、`capture failed=0`、`fps ≥ 设定−10%`。

**通路 2：HDMI 输入（`stream_hdmirx`，video40）**
适合接入 HDMI 输出的红外机芯/图传接收机，无需任何内核改动。
1. 接入 HDMI 源，`cat /sys/class/hdmirx/hdmirx/status` 变 `connected`（**当前为 `disconnected`**）。
2. 该节点**只支持 MPLANE**（实测 `single=0 mplane=1`），且不支持尺寸枚举 → **必须先完成 §4 A2**，再按源的实际尺寸 `S_FMT`。
3. 可用格式：`BGR3` / `NV24` / `NV16` / **`NV12`**（选 NV12 可直接复用现有 `pack_nv12`）。
4. `--rgb-dev /dev/video40`。
5. 判据同通路 1；额外核对 `status` 在运行中不抖回 `disconnected`。

**通路 3：MIPI CSI（需硬件已接 sensor）**
1. 本轮实测 `/dev/video0`、`video4`、`video11`、`video15` 的 `open()` **返回 ENODEV（No such device）**，即 rkcif 设备节点存在但**未绑定任何 sensor**。`video22`（rkisp_mainpath）能打开但上报 800×600 上限，同样是无 sensor 的空口值。
2. 因此判定：**当前板卡没有可用的 MIPI CSI 输入**，除非已接入 CSI 模组且设备树使能。
3. 若后续有 CSI 模组：先复测 `video22` 的尺寸上限与格式，再按 §4 A2（MPLANE）+ §4 A1（若为 UYVY）接入。
4. **若需改设备树/加 overlay 才能出图 → 属于修改板端系统，本轮禁止**（见 §6）。

## 6. 任务 C：不修改板端系统接入真实相机的规范

### 6.1 为什么「零修改」可行（本轮的实证依据）

1. **UVC 驱动已编译进内核**（`CONFIG_USB_VIDEO_CLASS=y`）→ 插上就有 `/dev/videoN`，不装包、不 `modprobe`、不改 `/etc`。
2. **所有 video 驱动都 `=y`**（`/lib/modules/.../drivers/media` 目录都不存在）→ 不存在「加载模块」这种运行时变更。
3. **权限已够**：`user` 在 `video(44)` 组，`/dev/video*` 为 `root:video` → 无需 udev 规则、无需 chmod。
4. **MIPI/HDMI 通路在驱动层已就绪**（CIF/RKISP/HDMIRX 全部 `=y`）→ 只要硬件接了、设备树已使能，就能出图。但本轮实测：rkcif 组 `open()` 返回 **ENODEV**（无 sensor），rkisp/hdmirx 仅支持 **MPLANE** 且 HDMI 无源；**若设备树未使能则不做**（改 dts 属修改系统）。
5. **本轮已用自建探针在板上编译并实际跑过**（`/tmp` 自建目录，跑完即删），未触发任何写系统路径的操作 —— 该方式本身即是「零修改接入」的可复现样例。

### 6.2 允许 / 禁止 清单

| 允许（不落盘、不改配置） | 禁止 |
|---|---|
| 插拔 USB/HDMI 相机 | `apt` / `pip` / `modprobe`（本板也不需要） |
| 在 `/tmp/<自建目录>` 编译与运行 | 写 `/usr`、`/etc`、`/opt`、`/home/user` |
| 读取 `/sys`、`/proc`、`/dev` | 改 udev 规则、改设备树 overlay、改内核参数 |
| 用板端已有的 `ffmpeg` / `gst-launch-1.0` 做对照 | 停/重启系统服务、改 CPU/NPU governor 与频率 |
| `rm` 自己 `/tmp` 目录 | `sudo`（全程不使用） |

## 7. 任务 D：双光谱对齐（时间同步 + 空间配准）

> 本轮按约定未实现。下面是可直接施工的两段式方案；**先软件后硬件，先配准后融合**。

### D1. 时间同步（软件阶段，优先级最高）

1. **打时间戳**：完成 §4 A3，使 `frame_t.ts_ms` 来自驱动单调时钟（不是 `now_ms()`）。
2. **配对策略**（在预处理线程里做）：对每个 RGB 帧 `ts_r`，从 IR ring 里选 `|ts_i - ts_r|` 最小的帧；若最小差 > `max_pair_delta`（建议 = 1 帧间隔，30 fps 即 33 ms）则**丢弃该 RGB 帧**并计数 `pair_drop`。
3. **插值**：若 IR 帧率低于 RGB，用最近邻，不做时间插值（避免引入伪运动）。
4. **落盘**：`run.log` 每帧追加 `pair_delta_ms`；SUMMARY 输出 `pair p50/p99/pair_drop`。
5. **验收**：p99 ≤ 1 帧间隔；`pair_drop ≤ 2%`；人为制造一路延迟（`--fps` 不一致或 `tc` 不可用时用不同 fps 模拟）时 `pair_drop` 应显著上升 —— 证明配对逻辑真的在工作。
6. **明确边界**：软件同步只能保证「帧对」在时间上接近，**不能消除曝光起始时刻差**；毫秒级严格同步需 D2。

### D2. 时间同步（硬件阶段，后续）

- 方案：RGB/IR 两 sensor 共用主时钟 `FSIN`（master/slave 触发），或用同一触发源的 GPIO 脉冲。
- 前置：确认两 sensor 支持外触发寄存器；确认板上可引出 GPIO。
- 验收：示波器测两路曝光起始沿差 ≤ 1 ms；连续 1000 帧无漂移。
- 风险：涉及接线与 sensor 配置，属硬件改动，需单独立项。

### D3. 空间配准（离线标定 → 板端查表）

**标定数据采集**
1. 两路同时取流（§B4），对准同一块标定板（棋盘格需在红外下可辨；若红外看不出图案，用加热/温差靶标，例如贴铜箔的棋盘格）。
2. 采集 ≥ 20 组同步帧对，覆盖画面四角 + 中心（保证 H 稳定），每组存 `rgb_XXXX.ppm` + `ir_XXXX.ppm`（现已支持 PPM 落盘）。
3. 记录两路分辨率与镜头参数（焦距、视场角），并存 `meta.json`。

**求解**
4. 各自检测角点 → 同名角点配对 → `cv2.findHomography(ir_pts, rgb_pts, RANSAC, 3.0)` 得到 `H_ir2rgb`（IR 像素 → RGB 像素）。
5. 输出 `align.json`：

```json
{ "H_ir2rgb": [[...],[...],[...]],
  "src": "ir 640x512", "dst": "rgb 1920x1080",
  "n_pairs": 24, "reproj_rms_px": 1.4,
  "method": "checkerboard+ransac", "date": "2026-11-XX" }
```

**验收**
6. 棋盘格重投影 RMS ≤ 2 px（RGB 坐标系）；在 RGB 图上画 IR 角点，肉眼应贴合。
7. 若 FOV 差异过大（IR 视场小于 RGB），标定板须铺满 IR 视场，并在 `align.json` 里记 `valid_roi`（有效重叠区）。

**板端使用**
8. `rk_pre.c` 增加 `pre_load_h(const char *align_json)` 与 `pre_map_pts(const float H[9], box_t *b, int n)`（IR 框 → RGB 框）。
9. 双光谱一致性判据：IR 框投影到 RGB 后与 RGB 检测框 IoU ≥ 0.3 → 视为同目标；对外只发一条告警（`modality: "dual"`），否则各发一条（`modality: "rgb"` / `"ir"`）。
10. 融合优先级建议：白天 RGB 为主、夜间 IR 为主（按 RGB 平均亮度阈值切换），避免双份告警噪声。

### D4. 板端接入点（改动最小化）

| 文件 | 改动 |
|---|---|
| `rk_types.h` | `frame_t` 增 `pair_delta_ms`；`box_t` 增 `mod`（0=rgb,1=ir） |
| `rk_stream.c` 预处理线程 | 按 D1.2 做配对，写 `pair_delta_ms` |
| `rk_pre.c/h` | 增 `pre_load_h` / `pre_map_pts`（3×3 齐次变换） |
| `rk_track.c` | 关联时把 IR 轨迹投到 RGB 坐标系再算 IoU（D3.9） |
| `rk_alert.c` | 告警 JSON 增 `modality`、`pair_delta_ms`、`h_rms` |

### D5. 验收指标总表

| 指标 | 目标 |
|---|---|
| 配对延迟 p99 | ≤ 1 帧间隔（30 fps → 33 ms） |
| 配对丢弃率 | ≤ 2%（稳定场景） |
| 重投影 RMS | ≤ 2 px（RGB 坐标） |
| 双谱一致率（同一目标同时被两路检出） | 记录基线值，不设硬门槛 |
| 告警重复率 | 同一目标同一时刻 ≤ 1 条 |
