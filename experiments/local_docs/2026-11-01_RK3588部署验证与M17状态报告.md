| 包 | 同时存在的 dist-info | 风险 |
|---|---|---|
| numpy | `1.26.4` **与** `2.2.6` | 目录只有一个 `numpy/`；pip 元数据双份，`import numpy` 实际版本取决于最后写入，**不可判定** |

约束：**不得改动板端已存在的任何文件、配置、系统设置及现有运行内容**。据此确定三条红线：

### 3.5 yolo26 v2：崩溃根因消除与数值正确性复核

#### 做了什么

结果 B 的段错误根因是检测头后处理（NMS-free 的 `v26Detect` 自带 `TopK` / `Mod` / `GatherElements`）。v2 用进程内 monkeypatch 绕过：

- `v26Detect.forward` → 只返回 `one2one` 分支的原始卷积输出（不再走 `postprocess`）
- `DualHeadFusionDetectV26.forward` → 只取 `branch_order` 里的 `fuse` 分支
- `torch.onnx.export(opset=12, do_constant_folding=False)`，输出 `p3/p4/p5` 三个裸特征图

产物留在服务器 `_d2p1/deploy_v2/`（未覆盖既有 `_d2p1/deploy/`）：

| 文件 | 大小 | 说明 |
|---|---|---|
| `yolo26_fuse_raw.onnx` | 20.59 MB | 1092 节点 / 19 种算子，**无 TopK / Mod / GatherElements / NMS / ScatterND** |
| `yolo26_fuse_raw.rknn` | 13.63 MB | rk3588 / fp16 / `do_quantization=False` / opt=3 |

导出时一个关键坑：`torch.onnx.export` 的 `torch.jit.trace` 在 CPU 上极慢（>25 分钟未结束），把模型和 dummy 张量搬到 CUDA 后**追踪+导出仅 8.4 秒**。

#### 崩溃已消除

### 3.7 校准集扩样（32 → 160）与量化算法（normal / mmse）对比

#### 做法

| 项 | 设置 |
|---|---|
| 校准集来源 | `mendeley_split/train` 的 **4 604 对** RGB+IR，**等距抽样**取 N 对（避免「只取前 32 张」造成的场景偏置） |
| 预处理 | 与板端严格一致：各自 resize 640×640 → IR 单通道转 3 通道 → 按通道 concat 成 6 通道 → /255 到 0..1 |
| 落盘 | 每张一个 `(1,6,640,640)` float32 `.npy`，`calibN.txt` 列绝对路径 |
| RKNN 配置 | `mean_values=[[0]*6]` / `std_values=[[1]*6]` / `quantized_dtype='w8a8'` / `quantized_method='channel'` / `optimization_level=3` |
| 自变量 | 只有两个：**校准集规模 N**（32 / 160）、**`quantized_algorithm`**（normal / mmse） |

#### 模拟器对数（基准：同一个 raw ONNX 的 ONNX Runtime fp32 输出）

逐输出计算 cos 相似度 / 平均绝对偏差 / 最大绝对偏差（p3、p4、p5 三个张量，两个真实样本 × 3 输出）：

| 模型 | N | 算法 | 体积 | 构建耗时 | cos（6 组） | mean_abs | max_abs |
|---|---|---|---|---|---|---|---|
| `yolo26_int8_normal8.rknn` | 8 | normal | 8.33 MB | 12.9 s | 0.99801 ~ 0.99924 | 0.185 ~ 0.306 | 2.94 ~ 6.71 |
| `yolo26_int8_normal32.rknn` | 32 | normal | 8.33 MB | 27.3 s | 0.9969 ~ 0.9989 | 0.217 ~ 0.341 | 4.48 ~ 11.21 |
| `yolo26_int8_normal160.rknn` | 160 | normal | 8.33 MB | 105.4 s | 0.9933 ~ 0.9989 | 0.22 ~ 0.33 | 5.0 ~ 12.2 |
| **`yolo26_int8_mmse8.rknn`** | 8 | **mmse** | 8.33 MB | **526.8 s** | **0.99892 ~ 0.99970** | **0.111 ~ 0.172** | 3.26 ~ 9.80 |

**扩样的效果：没有。** N=8 / 32 / 160 的 cos 区间几乎重合（0.9969~0.99924），平均绝对偏差同量级。对本模型（单类、输入分布稳定），**校准集从 8 扩到 160 不带来可测的量化精度提升**；扩样的真实价值是**覆盖更多场景/光照/距离开关**（稳健性，而非指标）。

**mmse 的效果：数值上确实更好，但有代价。**

| 对比（同为 N=8） | normal8 | mmse8 | 变化 |
|---|---|---|---|
| cos | 0.99801 ~ 0.99924 | 0.99892 ~ 0.99970 | ↑ 约 0.001 |
| mean_abs | 0.185 ~ 0.306 | 0.111 ~ 0.172 | **↓ 约 45%** |
| 构建耗时 | 12.9 s | 526.8 s | **× 41** |
| 板端 mAP50 | 0.9287 | 0.8981 | ↓ 0.031 |
| 板端 top1 IoU（vs ORT） | mean 0.8961 / min 0.7648 | mean **0.9009** / min **0.8295** | ↑ 框更准 |
| 分数绝对偏差（vs ORT） | mean 0.0467 / p50 0.0168 | mean **0.1158** / p50 0.1187 | **↑ 分数系统性偏低约 0.12** |
| 0.25 阈值下的检出帧 | 缺 0/26/27/32/33（均 < 0.25） | **多缺 frame 5**（ORT 参考 0.7586） | 多漏 1 帧 |

结论：**mmse 让框更准（IoU 提升、min IoU 从 0.765 提到 0.830），但把分数整体压低了约 0.12，在固定 0.25 阈值下反而多漏一帧。** 要用 mmse 就必须**重新标定阈值**（按分数分布下移约 0.12），否则不建议替换默认的 `normal`。

**mmse 的成本（决定它能不能用）**：`MmseQuant2` 是**逐层（300 层）+ 逐通道搜索**，每层都要在校准集上前向一遍，耗时**与 N 近似线性**：

| N | 实测速率 | 实测/估算总耗时 |
|---|---|---|
| 8 | 7.9 s/层 | **实测 526.8 s ≈ 8.8 分钟** |
| 32 | 31 s/层 | 估算 ≈ 2.5~3 小时（本模型 300 层） |
| 160 | 同比例放大 | 估算 ≈ 12 小时以上 |

也就是说：**mmse 只能在 N≤8 的小校准集上跑得起**；160 张跑 mmse 在工程上不可接受（成本远超收益）。工程建议：默认用 `normal` + 160 张（稳健性优先），只有在「框精度」是硬指标、且能接受重标阈值时才考虑 mmse + 小校准集。

### 3.8 板端检测头解码器与端到端精度验收

#### 为什么必须自己写解码

yolo26 的端到端头 `v26Detect.postprocess` 里有 `TopK / Mod / GatherElements` —— 这三个算子正是 DV-1（板端 `rknn_run` 段错误）的根因。本方案在导出时把两个检测头分支都 patch 掉：

- `v26Detect.forward` → 只返回 `one2one` 分支的 `cat(cv2, cv3)`
- `DualHeadFusionDetectV26.forward` → 只取 `fuse` 分支

于是 ONNX 的图里**没有任何后处理算子**，输出就是 3 个裸特征图 `(1,5,80,80) / (1,5,40,40) / (1,5,20,20)`（通道 5 = 4 个 box 的 ltrb + 1 个 cls，`nc=1`）。框的解码全部下沉到板端 C。

#### 解码公式（与 ultralytics `Detect._inference` + `dist2bbox` 逐项对齐）

```c
/* 网格中心：make_anchors(grid_cell_offset = 0.5) */
ax = gx + 0.5;  ay = gy + 0.5;
score = sigmoid(cls);                     /* 单类，无 objectness */
x1 = (ax - l) * stride;  y1 = (ay - t) * stride;
x2 = (ax + r) * stride;  y2 = (ay + b) * stride;
/* strides = [8, 16, 32] 对应 p3 / p4 / p5 */
```

**没有 NMS**：end2end 的 `one2one` 分支本身是 NMS-free 设计，`postprocess` 只做 `scores.topk(max_det=300)`。板端实现等价于「三层全格点打分 → 全局 top-k」，与参考完全同构。

#### 验收口径（保证板端和参考吃同一份字节）

| 项 | 做法 |
|---|---|
| 测试集 | `mendeley_split/test` **等距抽样 40 对**（与 train 无重叠） |
| 输入 | 打包成 `e2e_inputs_u8.bin`：**uint8、NHWC、640×640×6**，每帧 2 457 600 B，共 98.3 MB。板端与 ORT 读**同一份文件**，消除预处理差异 |
| 参考 | ONNX Runtime **fp32** 跑同一张 raw ONNX（不用 PyTorch 参考，避免把导出误差混进来） |
| 指标 | mAP@0.5（101 点插值）、P / R（score ≥ 0.25 且 IoU ≥ 0.5 记 TP）、meanIoU；GT 共 36 个框 |
| 对齐 | 板端 top1 与 ORT top1 逐框算 IoU 与分数偏差 |

#### 结果

| 口径 | mAP50 | P | R | meanIoU | n_det |
|---|---|---|---|---|---|
| **板端 int8 normal160** | **0.8899** | 0.8684 | 0.9167 | 0.8052 | 38 |
| 板端 int8 normal32 | 0.8909 | 0.9167 | 0.9167 | 0.8064 | 36 |
| 板端 int8 normal8 | 0.9287 | 0.9714 | 0.9444 | 0.8192 | 35 |
| 板端 int8 mmse8 | 0.8981 | 0.9706 | 0.9167 | 0.8412 | 34 |
| ONNX RT fp32（top3 口径） | 0.8680 | 0.8378 | 0.8611 | 0.8423 | 37 |

- **int8 板端没有掉精度**：四个 int8 变体 mAP50 都在 0.89~0.93，全部不低于 fp32 参考的 0.8680（差异主要来自 top-k 口径与 40 帧样本量，不代表量化比 fp32 更准）。
- 逐框对齐（normal160）：IoU `n=35 mean 0.8645 / p50 0.8820 / min 0.1327`；分数绝对偏差 `mean 0.0454 / p50 0.0296`。
- 逐框对齐（normal8 / mmse8）：IoU `mean 0.8961 / 0.9009`、`min 0.7648 / 0.8295` —— 校准集越小、mmse 越让**框**更贴近 fp32；但 mmse 的**分数**系统性偏低约 0.12（见 §3.7）。
- **5 个「无框」帧不是漏检**：frame 0 / 26 / 27 / 32 / 33 的 ORT 参考 top1 分数分别是 **0.1359 / 0.1286 / 0.0001 / 0.0 / 0.0016**，全部 < 0.25，板端正确地不输出框。mmse8 额外漏掉 frame 5（ORT 参考 0.7586），是其分数下移导致的阈值效应，不是解码错误。

#### 布局诊断（为什么可以确认解码方向是对的）

| 证据 | 结论 |
|---|---|
| `RKNN_QUERY_OUTPUT_ATTR` → `fmt=0(NCHW)`、`dims=[1,5,80,80]` | 属性声明是 NCHW |
| `RKNN_DUMP` 落盘首帧原始输出，与 `dump_ort.py` 的 ORT 输出**逐通道**算 cos | 5 个通道 cos 0.982 ~ 0.999；cls 通道 0.9991 / 0.9986 / 0.9935 | 
| 上述两项一致 | 数据确实是 NCHW 存放，**不是**「声明 NCHW 实际存 NHWC」的错位 |

#### 板端性能（int8 normal160，40 帧稳态）

| 项 | 数值 |
|---|---|
| 预处理（LUT 查表 0..1 → int8 scale，含 98 MB 测试文件读取） | 13.80 ms |
| NPU 推理 `rknn_run` | 64.06 ms（p50 63.36 / min 42.64 / max 83.42）→ **15.6 FPS** |

### 7.2 采集管线（V4L2 / MPP + ring buffer）

| 项 | 实测/实现 |
|---|---|
| MPP 硬解 | `decode_put_packet` + `decode_get_frame`；packet **只引用外部缓冲不拷贝**，4 块 × 256 KB 轮转；EOS 后持续 drain，连续 20 轮（≈100 ms）无新帧才收尾（小码流常见，提前退出会丢尾帧） |
| 帧率节拍 | 放在**真正入队出口** `emit()`，而不是解码循环里 —— 避免「解码快、ring 被打满」 |
| ring | `cap` 可配（`--ring 4`），生产者覆盖最旧帧并计数；实测两路 **pushed=59/299、overwritten=0、skipped=0、pre drop=0** |
| V4L2 路径 | 已实现（`CAP_V4L2`：`VIDIOC_S_FMT`/`REQBUFS`/`QBUF`/`DQBUF`，NV12）；**本板 41 个 `/dev/video*` 全部是 `rkcif`/`rkisp`/`hdmirx` 内核节点，无 USB/MIPI 相机接出**，按「不依赖真实硬件」的要求未做真机取流验证 |
| 裸 NV12 回放 | `CAP_FILE` 后端，用于把主机侧生成的 NV12 直接灌进流水线（对拍预处理用） |

### 7.3 预处理与坐标反变换

- 张量布局：`[B,G,R, Y,Y,Y]` 交错、值域 0..1、`640×640×6` NHWC；NV12→BGR 走 BT.601 limited 整数定点（`CY=1192、CVR=1634、CGU=400、CGV=833、CUB=2066`，`q=10`），与 ffmpeg 默认一致。
- 两种几何模式，反变换与预处理**严格互逆**：

| 模式 | 预处理参数（实测打印） | 反变换 |
|---|---|---|
| letterbox | rgb `1920×1080→640：scale=0.3333/0.3333 pad=(0,140)`；ir `640×512→640：scale=1.0 pad=(0,64)` | `x=(x_net-pad_x)/scale`，`y=(y_net-pad_y)/scale` |
| stretch | rgb `sx=0.3333 sy=0.5926`；ir `sx=1.0 sy=1.25` | `x=x_net/sx`，`y=y_net/sy` |

- 同一目标的实测框（**已在原图 1920×1080 坐标系**）：

| 模式 | 输出框 | 与 stretch 基准的差 |
|---|---|---|
| letterbox | `[1631.7, 482.5, 1756.6, 521.2]` | dx1 −2.3 / dy1 −1.5 / dx2 −2.4 / dy2 +5.2 |
| stretch | `[1634, 484, 1759, 516]` | 基准 |

两种几何路径对同一目标的结果相差 **≤5.3 px（<0.28% 帧宽）**，说明 pad/scale 分支反变换没有错位；letterbox 的 `dy` 偏大是因为纵向 1080→360 是 **3× 下采样**，y 边界量化粒度约 3 px。与 fp32 参考的残余偏差 ≤7 px，来自剪枝 + int8 的模型侧差异，不是坐标换算误差。

### 7.4 int8 直喂（关键性能优化）

| 项 | 数值 |
|---|---|
| 输入属性实测 | `type=2(INT8) scale=0.0039216(=1/255) zp=-128` |
| 旧路径（float32 整张 + 运行时归一化） | 主机侧整形 **88.1 ms**，整链 151~195 ms |
| 新路径（预处理线程内 `pre_quant_i8`，`pass_through=0 + INT8`） | 主机侧整形 **16~18 ms**，整链 **74~76 ms** |
| 坑 | `pass_through=1` 在本板运行时输出**全零**（该语义要求零拷贝内存），已验证 `pass_through=0` 与 float32 路径**逐帧结果完全一致**，故固定用 0 |

### 8.1 `round_to=8 / min_ch=8`（通道对齐）

[align8.py](file:///c:/Users/不如喝茶去/Desktop/双光谱毕设/scripts/deploy/rk3588/align8.py)：逐 Conv 记录 `in/out` 通道，规则 `target=(out//8)*8`，若 `target < min_ch(8)` 则不动，输出 `align_report.json`（`--strict` 有未对齐层时退出码 2）。

| 指标 | 值 |
|---|---|
| Conv 总数 | 170 |

**链路可追**：服务器 `model_int8.rknn` 与板端 `/tmp/.../pruned_int8.rknn` **MD5 完全相同**（`faf9ff91…`），板端 §7 全部实测用的就是这条流水线产出的模型。

**精度代价（重要）**：

| 模型 | ORT fp32 mAP50 | 板端 int8 mAP50 | NPU 耗时 |
|---|---|---|---|

## 9. 复现方式

### 9.1 主机侧：一条命令跑完剪枝 → 蒸馏映射 → 导出 → 对齐 → 校准 → 转换 → e2e 参考

```bash

    --weights best.pt --data-root /path/mendeley_split --work /path/work \
    --target rk3588 --precision int8 --algo normal --n-calib 160 \
```

分步等价（便于只重跑其中一步）：

```bash

    --student work/pruned/pruned.pt --out work/distill.yaml --mm-root /path/MutilModel_3485988898
# ④ 导出无后处理 raw 头（p3/p4/p5）
```
