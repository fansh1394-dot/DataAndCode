## 一、测试口径

| 维度 | 定义 |
|---|---|
| 告警触发密集度 | alerts/s（按墙钟时长）、每 100 处理帧告警数、告警/检测比 |
| 预警准确率 | 告警框与 GT IoU≥0.3 记为 TP，precision = TP/告警数；轨迹覆盖率 cov@0.3 = 有正确框的处理帧/有 GT 的处理帧 |
| 目标框选响应延迟 | GT 出现后首帧「有框」/「框命中」所需源帧数；以及同帧端到端延迟 e2e |
| 目标框选定位精度 | 每帧最佳轨迹与 GT 的 IoU 中位数、中心误差（px）、cov@0.3 / cov@0.5 |
| 跟踪稳定性 | 独立 track ID 数 / 100 处理帧、最长连续轨迹帧数 |

为避免检测误差掩盖跟踪算法本身的问题，另做一组 **GT 驱动（oracle）** 实验：把标注框当作完美检测输入离线回放跟踪器，单独度量跟踪/告警逻辑。

## 四、根因分析

### R1 跟踪/告警逻辑缺陷（已修复，确为「告警密集 / 框漂移」主因）
1. 预测步长固定为 1 帧：板端实际处理间隔 ~150 ms（源帧 50 ms），丢帧时卡尔曼预测严重欠调，关联失败 → 频繁新建 ID。
2. 关联只认 IoU≥0.35：6 fps 处理节拍下小/快目标相邻帧 IoU 骤降 → ID 频繁切换。
3. `hits` 每帧 miss 清零、新轨迹立即确认（UI confirm=1）→ 每个碎片轨迹立刻告警。
4. 无同轨迹冷却、无跨轨迹空间去重 → 同一目标 ID 切换后重复告警。
5. 输出卡尔曼滤波框而非最新检测框；轨迹丢失后仍输出最多 8 帧旧框 → 框滞后/漂移，即「框选位置不准」的次要来源。
6. 低置信检测可参与确认/告警。

- [match_score L105](file:///c:/Users/%E4%B8%8D%E5%A6%82%E5%96%9D%E8%8C%B6%E5%8E%BB/Desktop/%E5%8F%8C%E5%85%89%E8%B0%B1%E6%AF%95%E8%AE%BE/scripts/deploy/rk3588/runtime/rk_track.c#L105-L135)：IoU 主判据 + 中心距/尺度门限放宽；三阶段关联（0.25/0.15/0.05）。
- [预测步长 L209-L220](file:///c:/Users/%E4%B8%8D%E5%A6%82%E5%96%9D%E8%8C%B6%E5%8E%BB/Desktop/%E5%8F%8C%E5%85%89%E8%B0%B1%E6%AF%95%E8%AE%BE/scripts/deploy/rk3588/runtime/rk_track.c#L209-L220)：按实际 `dt` 倍率缩放，限制 0.5–4。
- [累计高置信确认 L173](file:///c:/Users/%E4%B8%8D%E5%A6%82%E5%96%9D%E8%8C%B6%E5%8E%BB/Desktop/%E5%8F%8C%E5%85%89%E8%B0%B1%E6%AF%95%E8%AE%BE/scripts/deploy/rk3588/runtime/rk_track.c#L173-L175)：`n_high≥confirm_n 且 age≥confirm_n`，允许短时空洞。
- [跨轨迹空间去重 L180](file:///c:/Users/%E4%B8%8D%E5%A6%82%E5%96%9D%E8%8C%B6%E5%8E%BB/Desktop/%E5%8F%8C%E5%85%89%E8%B0%B1%E6%AF%95%E8%AE%BE/scripts/deploy/rk3588/runtime/rk_track.c#L180-L198)：10 s 告警记忆，新轨迹继承冷却。
- [输出策略 L364-L368](file:///c:/Users/%E4%B8%8D%E5%A6%82%E5%96%9D%E8%8C%B6%E5%8E%BB/Desktop/%E5%8F%8C%E5%85%89%E8%B0%B1%E6%AF%95%E8%AE%BE/scripts/deploy/rk3588/runtime/rk_track.c#L364-L368)：命中帧直接输出检测框；丢失 >2 帧不再输出旧框；未确认轨迹也上屏保证框选及时。

### R2 检测模型域偏移（「框选位置不准 / 预警不准确」的主因）
当前 `model.rknn` 为 Mendeley 6 通道（EO+IR）数据训练，直接用于 Anti-UAV 素材：
- 检测层 precision 0.4%、recall 0.1%，IoU 中位 0.008，中心误差约 300 px；
- 85% 的处理帧零检测（单帧平均检测数 0.12–0.66）；
- 典型误检在画面左下角，GT 在右上，位置完全无关。
这属于训练域与部署域不匹配，任何跟踪算法都无法补救。

### R3 处理管线吞吐（「端到端延迟高 / 框选响应慢」的主因）
- 帧内耗时：预处理 62 ms（1920×1080 RGB→BGR + 灰度 + letterbox）+ NPU 56 ms ≈ 131 ms/帧，理论上限 ~7.6 fps；
- 实际 ~6 fps，源 20 fps → **丢帧 69%**，队列排队使 e2e 中位 176–192 ms、p95 233–250 ms；
- 跟踪器实测 **0.003 ms/帧**（1000 帧总耗时 3.3 ms），占总耗时 <0.01%，不是延迟来源。

### R4 素材/评估口径
- 演示用 `labeled_eo.mp4` 为 548 帧换镜拼接（相邻帧 GT IoU<0.1 占 498/547），不适合连续跟踪评估，本报告全部使用 Anti-UAV300 原生连续序列。

## 五、核心问题回答

### 问题 1：当前一系列异常是否由跟踪算法本身导致？

**部分是，但不是全部。** 逐项归因：

| 异常现象 | 主因 | 跟踪算法责任 |
|---|---|---|
| 告警触发过于密集 | 确认门限=1、无冷却/空间去重、ID 频繁切换后重复告警，每个碎片一次告警 | **主要责任（已修复）** |
| 框选位置不准确 | 检测模型域偏移（IoU 0.007、precision 0.4%）；其次旧版输出 KF 滤波框/丢失后仍输出 8 帧旧框 | 次要责任（旧框滞后部分已修复） |
| 目标框选响应缓慢 | 85% 帧无检测 → 首个框需等 ~2.5–3.2 s；且 6 fps 处理节拍 | 无（跟踪 0.003 ms/帧） |
| 端到端延迟高 | 预处理 62 ms + NPU 56 ms + 丢帧 69% 排队 | 无 |
| 连续序列跟踪不稳定 | 旧版固定预测步长 + 仅 IoU≥0.35 关联，6 fps 下 ID 抖动；GT 输入下 85.5 ID/段 | **主要责任（已修复，GT 输入降到 2.0 ID/段）** |

结论：**跟踪/告警逻辑确有一组真实缺陷，并直接造成了告警风暴、ID 抖动与框滞后；但「框不准」「响应慢」「e2e 高」的根因在检测模型域偏移与推理管线，不能归咎于跟踪算法。** 修复跟踪逻辑后，在同一批真实检测下告警量下降 90%，但定位精度仍受检测器限制。

### 问题 2：无人机场景是否需要单独的专项训练？

**需要，但只针对检测模型；跟踪器不需要训练。**

- 检测模型：**必须做无人机双光谱域专项训练/微调**。依据是检测 precision 0.4%、recall 0.1%、IoU 0.008，属典型跨域失效；需要 Anti-UAV / 真实无人机双光谱数据参与训练，并加入小目标、快速运动、低对比度（天空/逆光）样本与相应的跟踪友好增强（运动模糊、尺度抖动、JPEG 压缩）。训练完成后应重新做 int8 量化与阈值标定。
- 跟踪算法：属于经典 IoU 关联 + 卡尔曼滤波，无可学习参数，**无需训练**；本次通过逻辑修复 + 参数标定（confirm=3、冷却 10 s、三阶段门限、按 dt 缩放预测）已把 GT 输入下的 ID 数从 85.5 降到 2.0、告警密度从 1.9 降到 0.11 次/s。
- 后续如需更强关联能力（长时遮挡、多目标交叉），可考虑引入轻量外观特征（ReID）或学习型关联，但那属于算法升级，不是本次问题的必要条件。

## 六、后续建议（按优先级）

1. **检测模型域适配（最高优先级）**：用 Anti-UAV300 + 板端实拍双光谱数据微调，验收目标 det recall≥0.8、precision≥0.8（IoU 0.3），再重新量化部署。
2. **管线吞吐优化**：预处理 62 ms 可用 RGA 硬件缩放/色彩转换替代 CPU 逐像素循环，目标压到 <15 ms；或检测降频（10 fps）+ 帧间用卡尔曼预测维持框，可把 e2e 中位压到 100 ms 量级、丢帧率降到 <30%。
3. **阈值标定**：检测模型更新后重新按 ROC 标定 `thr / s_high / s_low / confirm_n / cooldown`，当前值基于旧模型。
4. 保留本次修复的跟踪器与告警策略（已通过 oracle 与真实数据双重验证）。

## 九、无法采集数据时的验收方案：公开数据集域适配 + 端侧实测（新增）

### 9.1 思路

现场采集不可行时，用**公开双光谱数据集**做域适配，把「模型准不准」变成可量化、可复现的答辩证据：

1. 训练只用 Anti-UAV300 `train`（160 序列 / 29716 帧对）；
2. 阈值与早停用 `val`（67 序列 / 12170 帧对）；
3. 验收只用 `test`（87 序列 / 16917 帧对）——**板端 6 段评测序列全部位于 test，且与 train/val 零重叠**（已用序列名集合求交验证，重叠数 0）；
4. 量化校准集从 `val` 等距抽 160 帧，**绝不使用 test 帧**，避免"用验收集校准"的方法论漏洞。

本机已具备条件：服务器 `/3250410011/root/rivermind-data/uav_data_v2` 就是由 Anti-UAV300 提取的 6 通道（EO 3ch + IR 3ch）成对数据集，含 `images/ images_ir/ labels/ labels_ir/` 与 train/val/test 划分。

### 9.2 与板端预处理对齐（关键）

原部署链路存在一处隐性错配：训练用 letterbox 保留长宽比，板端 `PRE_FIT_STRETCH` 直接拉伸到 640×640。YOLO 归一化标签在拉伸下不变，因此本方案先把数据集整体重采样为 640×640 拉伸版（`uav_data_s640`），使**训练/量化/板端三者口径完全一致**，标签无需重算。

### 9.3 训练与导出

- 结构：`yolo26n-mm-dual-fusion-concat`（与现网 `model.rknn` 同一骨架，保证板端 C 解码器无需改动）
- 数据：`uav_data_s640/data.yaml`，imgsz 640，batch 32，RTX 4090D，route A（随机初始化）
- val 第 8 轮：**mAP50 = 0.9895，mAP50-95 = 0.6328**（第 1 轮即 0.9628，第 3 轮起稳定在 0.97 以上）
- 导出：`export_onnx_raw.py` 取 fuse 分支原始特征图（3 输出 5 通道 = 4+1，无 TopK/NMS 等 CPU 回退算子，ONNX 20.6 MB）
- 量化：`convert_rknn.py --precision int8 --algo normal`，校准 160 帧 6 通道 0..1 浮点，输出 8.33 MB `.rknn`（与原模型同量级，`librknnrt` 直接加载）

### 9.5 答辩口径

- 「为什么不用现场数据」：现场采集不可行；Anti-UAV300 是公开双光谱无人机数据集，其 test 划分与训练集零重叠，等价于一次**留出集验收**。
- 「凭什么说模型准」：不但报了 val 指标，更报了**板端量化后**在 6 段未参与训练的真实连续视频上的检测 precision/recall、框 IoU、跟踪覆盖率与告警准确率。
- 「量化掉点多少」：同口径 int8 部署后 precision 0.995 / recall 0.851 / IoU 0.78，与 PyTorch 侧 0.9895 mAP50 的差距主要体现在极小目标，而非系统性崩坏。
- 已知短板：极小目标（1_7）召回偏低；预处理仍占 62 ms/帧导致 69.5% 丢帧。两者属于管线/小目标问题，不影响"跟踪算法本身无缺陷"的结论。

## 十、"同一目标多个框 / 目标数量虚高"专项修复（2026-11-04 追加）

### 10.1 现象与证据

部署界面上单个无人机会同时出现 2~4 个绿色/虚线框，"目标数量"卡片同步跳到 2~4。用 `--dump` 回放 6 段 bench 序列（1885 帧）统计：**12.9% 的帧存在 >1 个检测，单帧最多 3 个**，且这些框 IoU 高达 0.41~0.51（同一目标上的相邻网格峰值），确认属于误报。

### 10.2 根因（三层，逐层叠加）

1. **解码无 NMS**：`runtime/rk_model.c` 的 `infer_common()` 只做按分数排序后截断 `max_dets`，无锚框检测头在目标附近 2~4 个相邻网格响应都会作为独立检测输出 → 同目标多框。
2. **轨迹层重复新建**：`runtime/rk_track.c` 新建轨迹的重复判定只用 `IoU≥0.55`，而"小框嵌在大框内"的重复形态 IoU 只有 0.41 左右 → 新建出第二条轨迹。
3. **界面显示中间态**：`qt_ui/src/main_window.cpp` 把**全部轨迹**（含未确认的暂定轨迹、`lostFrames>0` 的预测框）和原始检测框都画上屏，且"目标数量"= `out.tracks.size()`。快速目标换 ID 时，旧轨迹的滞后框与新轨迹的当前框同时存在 → 用户看到"好几个框"。

### 10.3 修改内容（仅反无人机监测系统，未动其余功能）

| 文件 | 修改 |
|---|---|
| `runtime/rk_model.c` | 加入贪心 NMS（`NMS_IOU=0.35`）并对输出框裁剪到画布；排序后抑制同类高重叠框 |
| `runtime/rk_track.c` | 新建轨迹去重增加"包含度"判据：`inter/min(area) ≥ 0.70` 视为重复，不再新建 |
| `qt_ui/src/main_window.cpp` | 上屏只画**已确认轨迹中丢失帧数最少**的一组；"目标数量"直接取上屏框数（严格一致）；原始检测框改为仅 `UAV_DEBUG=1` 时显示；dump 增加 `confirmed` 字段便于回归验证 |

## 十一、双光谱视频显示链路排查（2026-11-04 追加）

### 11.1 结论速览

| 问题 | 结论 |
|---|---|
| Qt 界面是否显示双光谱？ | **否**。界面只显示可见光（EO）一路；红外（IR）只进推理，从不上屏 |
| 显示优先级 | **没有优先级逻辑**，主源 `m_src` 永远是显示源；不存在"红外优先" |
| 是否自动切换 | **没有**。无任何按条件切换 EO/IR 的代码路径 |
| 硬件是否同时输出 RGB + IR | **否**。当前板端未接入任何 USB 摄像头（lsusb 只有 HUB 与 WLAN） |
| 推荐方案 | **单路主显示（EO）+ 可切换/小窗 IR**，不并排铺满；需要双路同步喂 6 通道模型 |

### 11.2 现有显示链路（实测代码路径）

```
文件模式：
  用户选择 xxx.mp4 ──► VideoSource::openFile（ffmpeg 抽 ES → MPP 硬解 → NV12→RGB888）
                    └─► 若同目录存在 xxx_ir.mp4 ──► 第二个 VideoSource（同样解码）
  主线程 onTick(10ms) ──► m_src->takeLatest() ──► VideoWidget::setFrame(EO 帧)   ← 唯一上屏图像
                      └─► m_srcIr->takeLatest() ──► 只作为 requestProcess 的第二参数
                                                    └─► Kernel::processFrame(6ch)：EO→BGR 3 通道 + IR 亮度→3 通道

相机模式：
  connectCamera(单个 /dev/videoX, 1280x720@25) ──► VideoSource::runCamera（V4L2→NV12→RGB888）
  m_srcIr 被显式置空 ──► 永远走 processFrame(3ch)，IR 通道用 EO 亮度复制（单目降级）
```

关键代码位置：`qt_ui/src/main_window.cpp#L648-L681`（onTick 取帧上屏）、`#L476-L494`（`_ir.mp4` 配对）、`#L529-L592`（相机连接，只允许单设备）、`qt_ui/src/kernel.cpp#L84-L131`（3 通道兜底）、`#L133-L196`（6 通道双光谱）。

### 11.3 优先级与切换机制

- 显示源 = `m_src`，由用户打开的文件或 `connectCamera` 的单一设备决定；IR（`m_srcIr`）只存在于"文件 + 同名 `_ir.mp4`"这一条分支。
- 全文检索 `红外 / IR / m_showIr / QRadioButton / PIP`：无任何显示切换控件、无自动切换判据。
- 因此不存在"默认优先红外"，也不存在"按亮度/温度/置信度自动切 EO/IR"。

### 11.4 硬件实测（RK3588 板端）

```
lsusb：只有 2-1 QinHeng USB HUB、1-1 Realtek WLAN、各 USB 控制器
/sys/bus/usb/drivers/uvcvideo：有驱动、无绑定设备
/dev/video0..40：全部是 SoC 内部节点（rockchip-mipi-csi2 / rkisp / rkcif / stream_hdmirx），
                没有一个是 UVC 摄像头
```

结论：**当前没有任何 RGB 或 IR 视频从 USB 链路输出**。界面里看到的"双光谱"是本地 mp4 文件对（`labeled_eo.mp4` + `labeled_eo_ir.mp4`）回放，不是硬件实时流。

### 11.5 已发现的配置缺陷

1. `videos/demo_eo.mp4` 与 `videos/demo_ir.mp4` **不满足配对规则**（规则要求 `demo_eo_ir.mp4`），打开 demo_eo 会静默降级为单目。演示前需改名为 `demo_eo_ir.mp4` 或扩展配对规则。
2. 两路 `VideoSource` 各自按自己的 fps 节拍取最新帧，`onTick` 分别 `takeLatest`，**没有帧号/时间戳对齐**；IR 与 EO 不同步时，融合输入是"错帧组合"。当前两路同源同帧率时不明显，接真实双相机必须做配对。
3. 板端仍有旧回放进程残留（`uav_monitor --video labeled_eo.mp4 --autoplay`，无 `--exit-on-end`），会长期占用 NPU/CPU，演示前应清理。

### 11.6 显示方案结论与实现要求

**结论：单路主显示（EO 为默认主视图）+ IR 可切换（或右下角小窗/PIP），不采用并排双路铺满。**

判定依据：
1. 算法层已经把双光谱融合放在网络内部（P4/P5 中期 concat + 双头融合），操作员需要的是一张"结论画面"，不是两张原始图；
2. 反无人机判据（是否无人机、方位、距离）依赖可见光细节与彩色信息，IR 分辨率与细节不足以单独作为主视图；
3. 并排双路会把单块屏的有效像素减半，框选与告警横幅的可读性下降，且与现有单 VideoWidget 布局冲突；
4. 夜间/低照度时 IR 更有用，但这是"操作员手动切换"的诉求，不是自动切换能可靠判定的（自动切会丢掉彩色证据，误判成本高）。

实现要求（按优先级）：
1. **采集层**：`VideoSource` 增加双设备/双流入口（`openCameraPair(eoDev, irDev, w, h, fps)`），或支持相机 side-by-side 单帧拆图（左 EO / 右 IR）；IR 缺失时保持现有 3 通道兜底。
2. **同步层**：EO/IR 按帧序号 + 时间戳配对（容差 ±1 帧），替换现在各自 `takeLatest` 的隐式错帧；配不上时标记该帧为单目。
3. **显示层**：`VideoWidget` 增加 EO/IR 切换按钮与 PIP 小窗；IR 建议伪彩映射（灰度→inferno），并在角落标注当前视图；切换不影响推理与告警。
4. **产品层**：默认 EO，禁止自动切换；仅在 IR 视图下显示"红外模式"角标，避免把 IR 当可见光误读。
5. **演示层**：修正 `demo_eo.mp4` / `demo_ir.mp4` 命名，清理残留进程，确认 `视频源` 标签出现 `+ IR` 再开始演示。
