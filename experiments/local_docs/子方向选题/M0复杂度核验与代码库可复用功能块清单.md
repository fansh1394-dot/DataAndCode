## 第一部分：M0 朴素 Concat 的复杂度核验

### 1.1 结论

**是的，M0 是本项目架构中实现逻辑最简单的融合方式——但严格说，它不是"一个算子"，而是"零自定义代码"。**

关键事实：M0 的融合节点**没有调用任何项目自定义算子**。它用的是 ultralytics 原生的 `Concat` 层 + 原生 `Conv` 层：

```yaml
# cfg_local/yolo26n-mm-dual-fusion-concat.yaml L91-L103
# ---------------- 融合 neck (46-54)：朴素 Concat + 1x1 压回原通道 ----------------
- [[27, 39], 1, Concat, [1]]      # 46 (512ch)  P3: RGB256 + IR256
- [-1, 1, Conv, [256, 1, 1]]      # 47 (压回 256)
- [-1, 2, C3k2, [256, False]]     # 48 fuse P3
- [[30, 42], 1, Concat, [1]]      # 49 (1024ch) P4
- [-1, 1, Conv, [512, 1, 1]]      # 50
- [-1, 2, C3k2, [512, False]]     # 51 fuse P4
- [[33, 45], 1, Concat, [1]]      # 52 (2048ch) P5
- [-1, 1, Conv, [1024, 1, 1]]     # 53
- [-1, 2, C3k2, [1024, True]]     # 54 fuse P5
```

**自定义代码量 = 0 行**。`Concat` 与 `Conv` 均在 `tasks.py` 的标准分支处理（`L4128: elif m is Concat: c2 = sum(ch[x] for x in f)`），不进入任何多模态特判分支。

**为什么必须加 1×1 Conv**：直接 Concat 会让下游 C3k2 的输入通道翻倍（256→512），参数量与算力随之改变，M0 与 M3 的对比就不再是"只换融合算子"。1×1 压回原通道是为了**控制变量**。这 1×1 本身是原生层，不算融合逻辑。

### 1.3 四类融合范式的实现差异

| 维度 | M0 朴素 Concat | 注意力融合（CGA/CFT） | 交叉融合（CrossTransformer） | 门控融合（Gated） |
|---|---|---|---|---|
| **核心操作** | `cat([rgb, ir], dim=1)` | 注意力图生成 + 加权 | Q/K/V 投影 + softmax(QKᵀ/√d)V | `sigmoid(W·[rgb,ir])` |
| **参数量（相对）** | 1×（仅 1×1 Conv） | 1.5–3× | 5–15× | 2–3× |
| **计算复杂度** | O(C) 拼接 + O(C²HW) 的 1×1 | O(C²HW) 注意力 | **O((HW)²C) 二次方** | O(C²HW) |
| **实现行数** | **0** | 91（CGA） | 380（CTF） | 121 |
| **YAML 可表达性** | ✅ 纯原生层 | 需注册 4 个类 | 需注册 6 个类 | 需注册 1 个类 |
| **引入的失败模式** | 无 | 注意力熵→1 退化 | token 爆炸 / OOM | gate 塌缩到 0 |
| **RK3588 可部署** | ✅ 完全友好 | ⚠️ 软max 可导但算力高 | ❌ transpose 16K 限制 | ⚠️ grid_sample 风险 |

### 1.4 一个重要提醒：简单性 ≠ 性能劣势

实测数据（test 614 帧，mAP50-95）：

| 方案 | 实现复杂度 | mAP50-95 |
|---|---|---|
| **M0 Concat（0 行自定义代码）** | **最低** | **0.7645（最高）** |
| M3 Deformable（232 行） | 高 | 0.7609 |
| L4 ChannelPartition（237 行） | 高 | 0.7307 |

**约 1,500 行自定义融合代码，没有一个超过 0 行代码的 Concat。**

这印证了奥卡姆剃刀在本数据上的适用性，也说明 M0 作为基线是"强基线"而非"弱基线"——任何新方法必须超过 0.7645 才有意义。

## 第四部分：结论与建议

### 4.1 对问题 1 的最终回答

**已确认**：M0 是本项目中最简单的融合方式，且是**唯一零自定义代码**的方案。

但必须强调一个反直觉的事实：**在 1,500 行自定义融合代码（F1–F9 共 41 个模块）中，没有一个在 test 集上超过 0 行代码的 Concat（0.7645）**。

这使 M0 的性质发生了改变——它不是"弱基线"，而是**强基线**。论文里应明确表述为："在几何对齐、单目标占 99.3% 的数据条件下，朴素拼接已达到性能上界的 99% 以上，复杂算子无额外收益。"

### 4.2 对问题 2 的最终回答

**可替换功能块共约 70 个**，分四类：
- **A 类（30 个）**：已注册融合算子，改 YAML 即用
- **B 类（7 个）**：可拆用的子组件
- **C 类（6 个）**：多模态基础设施
- **D/E 类（12 个）**：数据层与诊断工具

**优先级最高的三个方向**：

1. **启用 `dual_loss.py` 里现成的三个加权项**（`fuse_ir_distill` / `fuse_ir_consist` / `gate_reg`）——代码已实现，零开发成本，直接针对 IR 旁路根因
2. **从 F9 的 25 个纯卷积算子中挑 3–5 个替换 M0 融合颈**——纯 YAML 改动，RK3588 全友好，可形成完整消融矩阵
3. **用 E3 诊断脚本预检任何新算子**——避免重演 part3h 的"训完 150 轮才发现 attn 空转"

### 4.3 风险提示

- `grid_sample` 类算子（F1–F4）在 RK3588 上**均为高风险**，且已有实测证明其在几何对齐数据上无收益
- Transformer 类（F7/F8）**参数暴增 + token 二次方**，在 640 输入下 P3 层 (80×80=6400 token) 必 OOM，除非强制降采样
- 所有新增算子必须先过 `_diag_part3h_attn.py` 的梯度探针，**确认非空转再投入 150 轮**
