# 双头 + 融合分支 · 验证期崩溃修复说明

**日期**：2026-09-24
**症状**：Kaggle T4×2 上 `--config dual-fusion` 训练到第一个 epoch 结束、进入验证时立即崩溃。
**结论**：已修复，并在本地 CPU 上复现 → 修复 → 回归验证全通过。

---

## 一、崩溃现象

训练主循环正常（进度条能打印 9 项 loss），但每轮结束调用 `_measure_validation()`
时抛错，训练中止：

```
RuntimeError: Validation loss dimension mismatch: got 9 items from model.loss(),
but validator expects 3 non-distill items ['box_loss', 'cls_loss', 'dfl_loss'].
```

关键点：**训练能跑、验证即崩**，所以不是模型/数据/显存问题，而是验证器的
「损失项数契约」与双头架构产出的项数不一致。

---

## 二、根因链路

三个检测头各自有 `box/cls/dfl`，`DualHeadDetectionLoss.forward` 按
`branch_order` 拼接，返回 **3 × 3 = 9 项**：

```
[box_rgb, cls_rgb, dfl_rgb, box_ir, cls_ir, dfl_ir, box_fuse, cls_fuse, dfl_fuse]
```

而 `MultiModalDetectionTrainer.get_validator()` 把这些固定为 3 项，
并**无条件**返回 `MultiModalDetectionValidator`：

| 环节 | 位置 | 行为 |
|---|---|---|
| 训练器写死 3 项 | `multimodal/train.py` `get_validator` | `self.loss_names = ("box_loss","cls_loss","dfl_loss")` |
| 验证器解析出 3 项 | `multimodal/val.py` `_get_non_distill_loss_names` | 从 `trainer.loss_names` 过滤蒸馏项 → 3 项 |
| 用 3 项建累加器 | `multimodal/val.py` L135 | `self.loss = torch.zeros(3, ...)` |
| 拿到 9 项后校验 | `multimodal/val.py` L230 | `if loss_items.numel() != 3: raise RuntimeError(...)` |

值得注意的是，**参考实现早就存在**：`models/yolo/detect/train.py::get_validator`
里已经有「双头 → 换用 `DualHeadDetectionValidator`」的 `isinstance` 分流，
只是 `multimodal/train.py` 这条多模态路径从未把这套分流搬过来。

### 连带发现的三个问题

修复过程中，把双头路径真正跑起来后，又暴露出三个会导致结果错误或崩溃的点：

1. **归一化不一致（影响结果可比性）**
   `dual_val.preprocess` 调 `super().preprocess()`，即 `DetectionValidator` 的
   **整图 `/255`**。但多模态 batch 是 `(B, 3+Xch, H, W)`，训练侧走的是
   precision contract（legacy+legacy 下 float 输入只对 RGB 三通道 `/255`、X 模态保原值）。
   整图 `/255` 会把 IR 通道压到与训练不同的值域 → 验证 mAP 与训练曲线不可比。

2. **IR 分支评测错帧（影响结果正确性）**
   `dual_val._swap_labels` 只替换 `bboxes`/`cls`，**没替换 `batch_idx`**。
   RGB 与 IR 每帧目标数可以不同（数据层为此专门提供了 `batch_idx_ir`，
   见 `data/augment.py` 与 `data/dataset.py` 的 collate）。
   若 IR 分支沿用 RGB 的 `batch_idx`，`_prepare_batch` 里
   `batch["batch_idx"] == si` 的掩码会切错目标 → IR 的 mAP 失去意义。

3. **两个契约缺失（导致崩溃）**
   - `validator.speed` 被置空 `{}`，而 `trainer._measure_validation` 会读
     `speed["preprocess"]` 等四项 → `KeyError`。
   - `_load_model_for_eval` 不认权重路径，而 `final_eval()` 以
     `validator(model=best.pt)` 调用 → 对 `Path` 取 `.names` → `AttributeError`。

4. **AFSS 打分链路不兼容（启用 AFSS 时才会暴露）**
   一旦 `get_validator` 分派到 `DualHeadDetectionValidator`，AFSS 启用后
   `score_epoch` 会拿到这个新验证器并要求它实现 `afss_score_batch`；
   而且它会**直接把原始前向输出**交给 `validator.postprocess(preds)` ——
   双头下那是 dict，`non_max_suppression` 会报
   `AttributeError: 'dict' object has no attribute 'shape'`。
   这是本次修复**引入的兼容缺口**（原代码走 `MultiModalDetectionValidator`，
   天然有这些方法），必须一并补齐。

## 三、修复内容

### `ultralytics/models/yolo/multimodal/train.py`

- 新增 `_is_dual_head_architecture()`：解包外壳后判断末层是否为 `DualHeadFusionDetect`。
- 新增 `_dual_head_loss_names()`：按 `rgb/ir/fuse` 展开为 9 项列名。
- `get_validator()`：双头架构 → 返回 `DualHeadDetectionValidator` 且
  `loss_names` 展开为 9 项；其余架构保持原行为不变。

### `ultralytics/nn/mm/dual_val.py`

- 新增 `BRANCH_LOSS_NAMES`：三头各 `box/cls/dfl` 的列名（与训练拼接顺序一致）。
- 新增 `_resolve_val_loss_names()`：**以 `loss_items` 实际长度为唯一真相源**，
  长度等于 `3 × n_branches` 时用分模态列名，否则回退 `trainer.loss_names`。
- `preprocess()`：改为 contract-aware（与训练同一套精度语义），
  并把 `batch_idx_ir` / `bboxes_ir` / `cls_ir` 一并搬到设备。
- `_swap_labels()`：**帧索引与框同源** —— IR 用 `batch_idx_ir`，其余用 `batch_idx`。
- `__call__()`：补 `Profile` 分段计时以填满 `speed` 四项契约；
  loss 累计改为「项数匹配才累计」；重复调用计数器复位。
- `_load_model_for_eval()`：接受权重路径，交给 `AutoBackend`。
- `postprocess()`：兼容双头原始 dict 输出（取主分支 `fuse` 后走父类 NMS）。
- 新增 `_select_main_branch()`：统一从双头 dict 里取主分支张量。
- 新增 `afss_score_sample()` / `afss_score_batch()`（含 `score_sample`/`score_batch`
  向后兼容别名）：补齐 AFSS 的 detect 适配器契约，使 `afss_enabled=True`
  在双头架构下也能正常打分。

## 四、验证结果

全部在本地 CPU（`pytorch-2.11.0-cpu`）完成，用小规模双标签数据集
（`synth_dual`，RGB 与 IR 框刻意错开、每帧目标数刻意不同）。

| 验证项 | 结果 |
|---|---|
| 修复前复现原崩溃 | ✅ 精确复现 `9 vs 3` 报错 |
| 修复后跑满 epochs | ✅ 训练 + 每轮验证 + `final_eval` 全部走通 |
| 三路 mAP 与融合增益产出 | ✅ 日志出现 `rgb/ir/fuse` 三套指标 + `fusion_gain_over_*` |
| `results.csv` 列完整 | ✅ 含 `train/{box,cls,dfl}_loss_{rgb,ir,fuse}` 与三路 mAP、增益 |
| 帧索引同源回归 | ✅ 9/9 通过（IR 帧0→2框、帧1→1框，与 RGB 相反且命中正确标签） |
| AFSS 开启兼容性 | ✅ `afss_enabled=True` 双头架构下打分链路跑通（3 epochs 完成） |
| Kaggle 补丁自校验 | ✅ 10/10 通过（打补丁结果与工作区源码逐字节一致） |

> AFSS 验证时把 `afss_fail_on_all_hard_after_scoring` 设为 `False`：合成集只有 5 张图
> 且模型未训练，按样本打分必然全 0，会被 AFSS 自带的「全 hard 即失败」守卫拦下。
> 这是该守卫在起作用，不是代码缺陷 —— 真实数据 + 训练后会自然越过。

`results.csv` 实际表头（节选）：

```
train/box_loss_rgb,train/cls_loss_rgb,train/dfl_loss_rgb,
train/box_loss_ir, ..., train/dfl_loss_fuse,
metrics/rgb/metrics/mAP50-95(B), metrics/ir/..., metrics/fuse/...,
metrics/fusion_gain_over_rgb, metrics/fusion_gain_over_ir
```

## 六、报数注意（沿用既有约定）

`ir` 头用 IR 坐标系标签（`infrared.json`），`rgb`/`fuse` 头用 RGB 坐标系标签
（`visible.json`），两者不同源 —— **三路 mAP 不可跨模态直接比大小**，
只能说「各自模态内，融合是否更优」。论文主指标取 `metrics/fuse/...`。
